**Як прибрати з історії (Q-07, лише з рішення власника):** старі значення є в трьох місцях: `main`, `develop` і службовому посиланні `refs/pull/1/head` (PR #1).
- **Варіант A — переписати історію.** (1) Вимкнути задачу cron-job.org (бот щогодини пушить у `main`). (2) `git filter-repo --invert-paths --path .env --replace-text <файл із замінами>` на повному клоні — хеші всіх комітів зміняться. (3) `git push --force` у `main`, видалити `develop`. (4) Попросити GitHub Support прибрати PR #1 і кешовані сторінки комітів — власник репозиторію сам цього не може. (5) Локальну папку перекачати наново (`git clone`) або `git fetch` + `git reset --hard origin/main`. (6) Перебазувати відкриті PR. (7) Увімкнути cron. Секрети, environments і налаштування Actions зберігаються.
- **Варіант B — новий репозиторій.** Видалити репозиторій на GitHub (разом із PR #1 і кешем) і створити з тією ж назвою з одним чистим комітом поточних файлів. Початкова рекомендація (до відповіді власника): якщо котрийсь із цих токенів/ключів ще діє — (1) @BotFather → `/revoke` для бота → новий токен; (2) Google AI Studio → видалити старий ключ, створити новий; (3) оновити секрети в GitHub (Settings → Environments `production`/`staging` або Secrets) і локальний `.env`. Переписувати історію git (`filter-repo`) **не обов'язково** — витік уже стався, допомагає лише заміна ключів.
Звідки взявся другий витік: тексти помилок `requests` містять URL з токеном. У логах Actions GitHub маскує секрети, але у файли, коміти й повідомлення адміну такі тексти потрапляти не повинні — пильнувати при змінах обробки помилок (зараз у звіти йде лише `resp.text`, ✔).

### ✅ A2. Якщо запуск «падає», стан не зберігається → ризик дублів у каналі — ВИПРАВЛЕНО 30.10 (PR #3, у `main` через #5)

Також губляться аналітика й лічильники невдалих перекладів (`translation_failures`), тож «погана» новина може пробуватися безкінечно.
