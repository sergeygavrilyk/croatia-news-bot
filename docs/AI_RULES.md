# Правила роботи AI-агента — Croatia News Bot

Адаптовано з `docs/AI_RULES.md` молдовського бота (який, своєю чергою, походить з `AI_RULES.md` проєкту croatian-survival-app). **Це джерело правди** для поведінки AI в цьому репозиторії; `CLAUDE.md` посилається сюди.

Специфіка цього бота, яка змінює правила порівняно з застосунком і з молдовським ботом:
- Немає «білда» й окремого стенду: **звичайний запуск `news_bot.py` з робочими секретами публікує в живий канал**. Для перевірок є тестовий режим `DRY_RUN` (з PR #4, T-05): пости — в адмін-чат з позначкою «ТЕСТ», файли стану не змінюються.
- Стан бота — **JSON/TXT-файли в самому репозиторії** (`posted_news.txt`, `posted_titles.txt`, `news_backlog.json`, `analytics.json`, `rejected_news.json`). Після кожного запуску GitHub Actions комітить їх у `main`. Тобто `main` змінюється щогодини без участі людини, а «база даних» — це git.
- Головні ризики — редакційні (що й як потрапляє в канал: дублі, геоблок, переклад) і вартісні (хвилини GitHub Actions, квоти Gemini), а не UX.
- «Контент» генерує Gemini в рантаймі, тому якість забезпечується промптами, фільтрами коду й моніторингом (звіт адміну), а не рев'ю перед публікацією.

## 1. Порядок дій (Operating Rules)

AI на кожну задачу:

1. Читає `project_state.md` (стан, відкриті питання, задачі) і релевантні розділи `docs/`. **Звіряє його з GitHub** (§2.2 п. 5): PR, змерджені або закриті після останнього запису журналу → оновлює статуси, §1 і YAML.
2. Оглядає наявний код (`news_bot.py`, `feeds.json`, workflow) і **свіжий** стан файлів у `origin/main` (робить `git fetch` — бот комітить щогодини; локальна копія майже завжди відстає).
3. Визначає залежності: файли стану, секрети й GitHub Environments (`production`/`staging`), cron-job.org, моделі Gemini, молдовський бот-близнюк.
4. Складає план і клас рішення (§3). Для `PROPOSE`/`HUMAN` — зупиняється й питає. Будь-яке нове чи змінене число (таймаут, повтор, поріг, ліміт, бюджет викликів) — завжди `PROPOSE` з варіантами (§2.2 п. 2).
5. Реалізує. Якщо змінюється правило — спершу знаходить усі місця, де воно застосовується (§2.2 п. 7).
6. Перевіряє (§5 Release gate) — без публікації в основний канал.
7. Звіряє з критеріями приймання задачі.
8. Оновлює документацію: `project_state.md` (завжди), `docs/AUDIT.md`, `docs/ARCHITECTURE.md`, `README.md` — що зачеплено.
9. Звітує (§6).
10. Пропонує наступні задачі (§6).

## 2. Заборонено без погодження людини (AI Must Not)

- змінювати **редакційну політику**: аудиторію каналу (українці в Хорватії, фокус — Задар), категорії «що публікуємо», стоп-теми, геоблок, тон, мову, правила хештегів — тобто зміст промптів у `deduplicate_news()` і `_build_translation_prompt()`, а також списки `SPORTS_PATTERN`, `AD_PATTERN`, `LEGACY_UNWANTED_KEYWORDS`, `UKRAINE_KEYWORDS`;
- додавати чи прибирати **RSS-джерела** у `feeds.json`;
- **запускати `news_bot.py`** або workflow з робочими секретами (це публікація в канал і коміт стану в `main`) і надсилати повідомлення в канал чи адміну; тестовий запуск `DRY_RUN` — теж лише з дозволу (він шле повідомлення в адмін-чат і витрачає запити Gemini);
- **вручну редагувати або чистити файли стану** (`posted_news.txt`, `posted_titles.txt`, `news_backlog.json`, `analytics.json`, `rejected_news.json`): помилка тут = дублі в каналі або втрачені новини;
- **мовчки змінювати формат файлів стану** (поля елемента беклогу, структура `analytics.json`);
- змінювати **моделі Gemini**, частоту запусків, `BATCH_SIZE`, `MAX_CANDIDATES_PER_FILTER`, `MAX_AGE_SECONDS`, паузи — усе, що впливає на вартість, квоти або обсяг публікацій; так само **таймаути, кількість повторів, пороги, ліміти й денні бюджети викликів** (`GEMINI_TIMEOUT_MS`, `TELEGRAM_TIMEOUT_SECONDS`, `SHARED_MODEL_TRANSLATE_BUDGET`, `MODEL_PROBE_INTERVAL_SECONDS`, `STOP_WORDS_DESCRIPTION_CHARS` тощо) — і нові такі константи теж;
- вмикати платні функції або **збільшувати витрати** (бюджети GitHub, платний тариф Gemini);
- змінювати видимість репозиторію, секрети, токени, доступи, GitHub Environments, задачі cron-job.org;
- переписувати історію git (`push --force`, `filter-repo`) — у т. ч. для видалення старих секретів: спершу рішення власника;
- додавати нову інфраструктуру (БД, хостинг, черги) або нові залежності;
- пушити або мерджити в `main` без явного дозволу; писати напряму в локальну папку власника (усі зміни — гілка → PR → погодження → `git pull`, R-08).

### 2.1. Жодних «тихих» змін (уроки 19–20.10.2026)
Під час рефакторингів AI-асистенти (Gemini) кілька разів **без погодження** переписували промпти своїми «базовими шаблонами», прибирали стоп-слова, фільтр гомогліфів, обрізку беклогу, спрощували звіт — власник помічав це лише постфактум. Тому:
- змінювати **лише те, що названо в задачі**; промпти й редакторські списки — дослівно, без «покращень», перефразувань і скорочень;
- **ніколи не видавати «повний новий файл»** замість точкових змін: лише diff/PR, де видно кожен рядок;
- у кожному PR — розділ **«Що видалено або спрощено»** (навіть якщо «нічого»), і окремо: чи змінювались тексти промптів (так/ні; якщо так — diff промпту в описі PR) і редакторські списки (так/ні) — повний формат опису в §2.2 п. 3;
- якщо зміна прибирає функцію/перевірку або зменшує кількість рядків помітно більше, ніж очікує задача, — зупинитись і спитати;
- поради про параметри моделей (напр. `thinking_budget`) — лише перевірені на реальному API (`check_models.py`/тестовий запит), не «з пам'яті».

### 2.2. Погодження, PR і документація (уроки аудиту 07.11.2026, T-30 → R-26)
Аудит PR #9–#30 (T-30) знайшов відхилення, яких «тихі зміни» з §2.1 не покривали. Власник погодив 7 правил для обох ботів (R-26):

1. **Промпти й редакторські списки — лише повністю погоджений текст.** Якщо в тексті є хоч одне слово, якого власник не бачив в остаточному вигляді (доповнення «за описом варіанта», стилістична правка, інший порядок слів), — зупинитись, показати остаточний текст повністю і чекати «так» **до** PR. Позначки «на перевірку в PR» заборонені. _(Урок: R-21 — друге речення КРОКУ 5.2 дописав Claude, погоджено лише постфактум, R-25.)_
2. **Числа — `PROPOSE`.** Таймаути, повтори, пороги, ліміти, бюджети викликів (нові й змінені): спершу варіанти з обґрунтуванням і «так» власника, потім PR. _(Урок: PR #11 — таймаути 180 → 90 с і 60 с; PR #22 — бюджет 8 — без окремого «так».)_
3. **Опис PR** — обов'язкові розділи:
   - «Що видалено або спрощено» (навіть «нічого»);
   - «Промпти змінено: так/ні» (якщо так — diff промпту);
   - «Редакторські списки змінено: так/ні» (`SPORTS_PATTERN`, `AD_PATTERN`, `LEGACY_UNWANTED_KEYWORDS`, `UKRAINE_KEYWORDS`, `HOMOGLYPHS`; якщо так — diff);
   - до кожної зміни промпту чи списку — **цитата «так» власника** з датою й часом;
   - **статистика diff** — вивід `git diff --stat origin/main...HEAD`, без словесних оцінок на кшталт «змінено лише 6 рядків».
   _(Урок: PR #14 — зміни стоп-списків лише в «Що видалено»; PR #22 — «6 рядків» при +115.)_
4. **Без ланцюжків PR.** Кожен PR — окрема гілка від свіжого `origin/main` і не містить комітів іншого відкритого PR. Якщо зміна залежить від відкритого PR — чекати його мержу або об'єднати все в один PR (а зайвий закрити з поясненням). _(Урок: PR #3/#4 потрапили в проміжну гілку; PR #22 ← #21, #29 ← #28, #30 ← #29.)_
5. **Документація після мержу.** На початку кожної сесії: `gh api "repos/<owner>/<repo>/pulls?state=closed&sort=updated&direction=desc&per_page=20"` → для кожного PR, змердженого чи закритого після останнього запису журналу, — запис у §7, статуси ✅ у §3/§4, §1 «Остання версія коду» і YAML (`active_tasks`, `technical_debt`, `last_updated`). Час для «Останнє оновлення» і журналу — з годинника (`TZ=Europe/Warsaw date '+%d.%m.%Y, %H:%M'`) **безпосередньо перед комітом**, не оцінка й ніколи не в майбутньому. _(Урок: D-35 — §1 відставав з 31.10; час «11:15» записано об 11:04.)_
6. **Відповіді власника — цитатою з часом.** У `project_state.md` відповідь записується дослівно в «лапках» з датою й часом (Europe/Warsaw). Якщо відповідь суперечить даним (скріншот, `analytics.json`, код, GitHub) — спершу перевірити й показати розбіжність, лише потім будувати план. _(Урок: Q-08 — записано «ключі в окремих проєктах, квоти не спільні», скріншот показав протилежне; PR #22 спроєктовано на хибній основі.)_
7. **Повнота зміни правила.** Коли змінюється правило (стоп-слова, ліміт, перевірка, поріг, бюджет), знайти **всі** місця, де воно застосовується (`grep` за константою, списком, назвою функції: скрейпер, фільтр, переклад, сувора перевірка, звіти), перелічити їх в описі PR і на кожне — тест. _(Урок: D-30 — «заголовок + лід» змінено в скрейпері, але не в `validate_translation_strict()`; D-26 — бюджет застосовано до всіх моделей, а не лише до `3.6-flash`.)_

## 3. Класи рішень

| Клас | Що | Приклади |
|---|---|---|
| **AUTO** — роби сам, потім звітуй | Внутрішня реалізація без зміни поведінки в каналі та вартості | рефакторинг, логування, обробка помилок, виправлення багів без зміни політики, тести, документація, `project_state.md` |
| **PROPOSE** — запропонуй план, чекай «так» | Архітектура, залежності, формат файлів стану, моделі Gemini, розклад/частота, пороги (12 год, 25 кандидатів, 3 пости, ліміти символів), таймаути, повтори, бюджети викликів (§2.2 п. 2), зміни workflow, перенесення змін з/у молдовського бота | заміна моделі, `if: always()` у workflow, перехід на Supabase, таймаут Gemini 180 → 90 с, денний бюджет 8 викликів |
| **HUMAN** — лише людина | Редакційна політика й аудиторія, джерела, бюджет і платні сервіси, видимість репозиторію, секрети, переписування історії git | «публікувати спорт?», «додати Antena Zadar?», «відкликати токен?» |

Сумнів між класами → обирай суворіший.

## 4. Definition of Done

Зміна готова, лише коли:

- ✓ вимоги задачі виконані;
- ✓ критерії приймання перевірені;
- ✓ код проходить `ruff check .` і `pytest -q` (workflow «Tests» на PR);
- ✓ тести в `tests/` на змінену поведінку (без мережі: Gemini, Telegram, сайти — підмінені) — на **кожне** місце, де застосовується змінене правило (§2.2 п. 7);
- ✓ перевірка без публікації в основний канал: тестовий запуск `DRY_RUN` (README «Типові операції») — обов'язково для змін у промптах, моделях і джерелах; запускає власник або Claude з його дозволу (це реальні запити до Gemini й повідомлення в адмін-чат);
- ✓ обробка помилок: збій Gemini/Telegram/джерела не губить статті, не публікує неперевірене й **не губить стан** (історію опублікованого);
- ✓ аналітика: якщо змінюється воронка — `analytics.json` і звіт адміну відображають зміну;
- ✓ вплив на вартість оцінений: хвилини Actions на запуск, кількість запитів Gemini на добу (квоти free tier);
- ✓ зміни формату файлів стану — сумісні зі старими файлами (бот читає те, що вже лежить у `main`);
- ✓ в описі PR є «Що видалено або спрощено», «Промпти змінено: так/ні», «Редакторські списки змінено: так/ні», цитати «так» власника до змін промптів і списків і `git diff --stat` (§2.1, §2.2 п. 3);
- ✓ PR не містить комітів іншого відкритого PR (§2.2 п. 4);
- ✓ документація і `project_state.md` оновлені; час — з годинника перед комітом (§2.2 п. 5);
- ✓ немає критичної регресії (бот публікує, звіт адміну приходить, коміт стану після запуску є).

## 6. Звіт після кожної завершеної задачі

AI повертає:

- **Зроблено** — що змінено (файли, коміти, PR).
- **Перевірки** — які пункти gate пройдені, які ні.
- **Аналітика й вартість** — вплив на воронку, запити Gemini, хвилини Actions.
- **Відомі обмеження.**
- **Технічний борг** — нове → `D-NN` у `project_state.md`.
- **Редакційні ризики** — що може гірше потрапляти/не потрапляти в канал, ризик дублів, мова перекладу.
- **Ризики стабільності** — залежність від моделей, джерел, лімітів, конфліктів комітів стану.
- **Рекомендовані 3 наступні задачі.**

AI може пропонувати пріоритети. **Остаточне рішення щодо пріоритетів — за власником (Product Owner).**

## 7. Project state

```yaml
project: croatia-news-bot
status:            # running | stopped | degraded
last_successful_run:
schedule:          # cron-job.org, частота
models:
  filter:          # каскад моделей для фільтра
  translate:       # каскад моделей для перекладу
sources:
  ok:
  error:
github_actions:
  repo_visibility:
  failed_runs_7d:
open_questions:    # Q-NN
active_tasks:      # T-NN в роботі
blocked_tasks:
technical_debt:    # D-NN
risks:
last_updated:
```
